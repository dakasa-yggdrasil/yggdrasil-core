# Deployment guide

Yggdrasil is manifest-first all the way to install. The deployment
model is:

1. Bring up a small **seed** stack somewhere you can `docker compose`
   or run a binary — Postgres + core + the two bootstrap adapters
   (kubernetes, schema-migrations).
2. Apply a `control_plane` manifest that declares the shape of the
   production deployment (replicas, ingress, transports, target
   cluster).
3. Run `yggdrasil deploy control-plane` — the seed dispatches
   `yggdrasil-deploy-control-plane`, which applies the rendered
   Kubernetes objects into the target cluster via the
   integration-kubernetes adapter and runs migrations via
   integration-schema-migrations.

The seed itself can live on a laptop, in CI, or as a small persistent
pod. The production control plane lives wherever the
`control_plane.spec.kubernetes.cluster_ref` points — a different
cluster, another namespace, whatever.

No Helm chart ships. Kubernetes-native install is driven by the
**Operator** (see [roadmap](#roadmap)) which watches control_plane
manifests and reconciles them automatically — same shape as the
deploy workflow, just event-driven instead of one-shot.

## 1. Seed — Docker Compose (dev, CI, small self-hosted)

Zero-configuration bootstrap. Ships the compose file + .env, runs
`docker compose up -d`. `yggdrasil init` automates it end-to-end (see
[getting-started.md](./getting-started.md)).

File: [`docker-compose.standalone.yml`](../docker-compose.standalone.yml).

Starts:

- **postgres** — state store.
- **yggdrasil-core** — the control plane. HTTP-only by default.
- **integration-kubernetes** — HTTP adapter on port 8081. Mounts
  `~/.kube/config` from the host so it can reach any cluster the
  operator can reach.
- **integration-schema-migrations** — HTTP adapter on port 8082.

After the core is ready, `yggdrasil init` POSTs two
`integration_instance` manifests pointing at the two adapter
services — so every workflow that needs them resolves a live
instance from the catalog.

Good for: laptops, demos, CI, single-host self-hosted deployments for
≤ 50 adopters. Default passwords come from `.env` (random when
generated by `yggdrasil init`). Persistence lives in named Docker
volumes — `docker compose down` is safe; `docker compose down -v`
wipes data.

Not good for: multi-node HA, cluster-backed persistence, centrally
managed secrets. For those, promote the seed to a Kubernetes control
plane via `yggdrasil deploy control-plane` (next section).

### Optional: AMQP transport backend

The AMQP backend (`rpc.Transport`) is opt-in. Run the compose with
the `amqp` profile if any integration declares `transport: rabbitmq`:

```sh
docker compose --profile amqp -f docker-compose.standalone.yml up -d
```

Otherwise the core runs HTTP-only and no broker is touched.

## 2. Production — `yggdrasil deploy control-plane`

The seed is the bootstrap. To run production in Kubernetes, write a
`control_plane` manifest and apply it through the seed:

```yaml
# control-plane.yaml
apiVersion: yggdrasil.io/v1alpha1
kind: control_plane
metadata:
  name: primary
  namespace: global
spec:
  image: ghcr.io/dakasa-yggdrasil/yggdrasil-core:v1.0.0
  replicas: 2
  resources:
    requests:
      cpu: 200m
      memory: 256Mi
    limits:
      cpu: 1
      memory: 1Gi
  postgres:
    mode: external
    external:
      host: my-db.internal
      port: 5432
      database: yggdrasil
      username: yggdrasil
      password_ref: secret://yggdrasil-db/password
      ssl_mode: require
  ingress:
    enabled: true
    host: yggdrasil.example.com
    class_name: nginx
    tls_secret_name: yggdrasil-tls
  kubernetes:
    namespace: yggdrasil
    cluster_ref:
      namespace: global
      name: production-cluster
```

```sh
yggdrasil deploy control-plane -f control-plane.yaml
```

The command:

1. POSTs the manifest through `POST /api/v1/manifests?kind=control_plane`.
2. Dispatches the `yggdrasil-deploy-control-plane` workflow with the
   manifest namespace + name as inputs.
3. Prints per-step progress (render → apply-infra → wait-infra →
   migrate → apply-core → wait-core).

See [features/manifests.md#control_plane](./features/manifests.md) for the
full spec surface (transports, bundled Postgres, resource claims,
overlays).

## 3. Custom / bare-metal core

You don't need Docker. Yggdrasil-core is a single Go binary.

```sh
export DB_HOST=localhost DB_PORT=5432 DB_NAME=yggdrasil \
       DB_USER=yggdrasil DB_PASSWORD=xxx \
       PORT=9080
./goose up               # once, after each upgrade
./yggdrasil-core         # starts serving
```

The HTTP API is always served on `PORT`. Additional `rpc.Transport`
backends are opt-in — set their env vars only if you need them (e.g.
`BROKER_URL=amqp://user:pass@localhost:5672/` enables the AMQP
backend; other transports expose their own config variable).

For first-run bootstrap add:

```sh
export YGGDRASIL_BOOTSTRAP_ADMIN_USERNAME=admin \
       YGGDRASIL_BOOTSTRAP_ADMIN_PASSWORD=your-strong-password \
       YGGDRASIL_BOOTSTRAP_MANIFESTS_PATH=/app/docs/bootstrap/seeds
```

Manage the process with systemd, supervisord, or whatever fits your
environment. Register the adapter instances manually via
`yggdrasil apply -f <instance.yaml>` if you want the deploy
workflow to run against this installation.

## Upgrades

See [upgrade.md](./upgrade.md). Short version: the schema is
goose-versioned and additive across patch versions; run `goose up`
and restart. Minor/major upgrades may deprecate manifest fields —
the release notes list them individually.

## Backup and restore

Yggdrasil state lives entirely in Postgres. Use your standard
Postgres backup (`pg_dump`, WAL archiving, managed snapshot). Any
`rpc.Transport` backend state is transient (e.g. AMQP queues are
re-declared on boot by the adapters themselves).

Restore = restore Postgres + bring any transport backends back up +
start the pods. Integration adapters recover autonomously.

## Observability

- `/healthz` — process liveness.
- `/readyz` — process + Postgres reachable.
- Structured logs on stdout (zap JSON).
- `event_log` table is your audit trail; tail it or pipe to your
  data lake.
- For metrics, wire a Prometheus endpoint via a surface (the
  first-party console exposes `/metrics`).

## Roadmap

- **Kubernetes Operator** — a controller that watches `control_plane`
  manifests and reconciles them automatically, replacing one-shot
  `yggdrasil deploy control-plane` with continuous reconciliation.
  GitOps-friendly.
- **OCI-based integration registry** — `yggdrasil install
  oci://ghcr.io/org/integration-foo` in place of GitHub-URL lookup.
- **Transport plugins via hashicorp/go-plugin** — transports become
  separately-distributed processes rather than compiled-in packages,
  so adopters can plug any RPC backend without forking the core.

## What used to be here

Earlier versions shipped a Helm chart (`chart/`). It was removed in
favor of the manifest-first deploy path above: every install
decision is now a `control_plane` manifest field, which is:

- **Versioned + audited** — the manifest lands in the same event log
  as every other catalog object.
- **Cluster-agnostic** — the same manifest renders against any
  cluster the integration-kubernetes instance can reach.
- **Extensible** — adding a new deploy knob is a schema field on
  `ControlPlaneManifestSpec`, not a new templated `{{ .Values... }}`.
  Plug-in transports and operator reconciliation compose on top
  without a chart rewrite.
