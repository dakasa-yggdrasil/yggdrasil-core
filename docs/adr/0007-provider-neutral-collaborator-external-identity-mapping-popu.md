# ADR-0007: Provider-neutral collaborator↔external-identity mapping, populated via reactor envelope + webhook receiver

- **Status:** Accepted
- **Date:** 2026-05-16
- **Deciders:** unknown
- **Scope:** yggdrasil-core (`internal/externalidentity/`), integration-slack, integration-google-workspace, integration-github (opt-in adapters)
- **Supersedes:** —
- **Superseded by:** —

## Context

Reactors (notably offboarding) need to act on the correct provider-side entity for a given collaborator (e.g. deactivate the right Slack user ID, not just "the collaborator"), but yggdrasil-core must stay neutral to provider-specific identifier semantics, and adapter binaries must not be required to call back into core's HTTP API just to resolve or persist that mapping.

The reactor framework's `on_collaborator_offboarded` for GitHub non-EMU orgs surfaced the structural gap concretely: onboarding via email-invite returns only an invitation ID, not the eventual GitHub username the invitee will actually have once they accept. Offboard fires knowing only `primary_email`, and `removeUserFromOrg(username=primary_email)` 404s silently — the user is never actually removed from the org. Slack and Google Workspace have the same underlying shape (email known at onboard, provider ID needed at offboard) and only "worked" by coincidence (their adapters happened to also support email-based lookup at offboard time), not because of any real contract. The correct fix is to persist provider-side identifiers at link time and make them available to later reactor invocations — without yggdrasil-core ever knowing about Slack, GitHub, or Google Workspace by name, without adapters depending on each other or calling back into core's HTTP API, and while supporting multi-instance (the same person can have different IDs in different Slack workspaces).

## Decision

Add a single core-owned table, `collaborator_external_identities`, and wire it into the reactor dispatcher and a new webhook receiver, entirely inside yggdrasil-core:

- `collaborator_external_identities (collaborator_id, integration_instance_id, external_id, external_metadata jsonb, linked_at, last_seen_at, unlinked_at)` — soft-delete via `unlinked_at`, with a partial unique index enforcing at most one **active** row per `(integration_instance_id, external_id)` while historical rows coexist. `external_id` must be the provider's **stable, opaque** identifier (Slack `U…` id, GitHub numeric id — never the mutable login/handle/email); mutable display info goes in `external_metadata`.
- **Read-side (reactor dispatcher):** before invoking any reactor capability, the dispatcher pre-populates `_context.external_identity` by looking up the collaborator's identity for that integration instance and embedding it in the request context. Adapters that need the provider-side ID (e.g. `on_collaborator_offboarded`) read it from context instead of re-deriving it from email or calling back into core.
- **Write-side (reactor dispatcher):** after a reactor call succeeds, the dispatcher extracts `output._yggdrasil.external_identity {external_id, external_metadata}` from the adapter's response (if present) and persists it via an idempotent `Upsert`. This is how adapters opt in to writing identity links — e.g. Slack/Google-Workspace on `on_collaborator_created`/`scim_apply_user`. Failure to persist is logged but never fails the reaction — identity is metadata, not core lifecycle state.
- **Upsert semantics** are a 3-way state machine: no active/unlinked row → INSERT (`inserted`); an unlinked row for the same `(collaborator, instance, external_id)` → re-activate (`re_linked`); an active row for the same collaborator → refresh metadata (`refreshed`); an active row for a **different** collaborator on the same `(instance, external_id)` → reject as `conflict` (`ConflictError`, neither row mutated, operator must reconcile) — the system never silently reassigns an external identity between collaborators.
- **Webhook receiver:** `POST /api/v1/integrations/{instance_id}/webhook` accepts provider payloads, verifies the HMAC signature per a core-owned signature-scheme registry (`github_hmac_sha256`, etc. in `hmac.go` — adapters do NOT implement signature verification themselves), forwards to the adapter's `on_webhook` capability, and executes the typed `actions` the adapter returns (`link_identity`, `unlink_identity`, `emit_event`) — unknown action kinds are logged and skipped, forward-compatible without a core release. This is how identity links driven by inbound provider events (e.g. GitHub `member` webhook) get applied, without the adapter holding core credentials.
- **Drift detection:** a daily cron (`resync_runner`) calls each opted-in adapter's `list_identities` capability and diffs the live provider list against the DB, emitting `drift_detected` (DB row with no matching live entry) or `unknown_external` (live entry with no DB row) — no auto-remediation, operator decides. Emission is rate-limited to once per 24h per identity via the same in-process debounce pattern used by `runtime_state.contract_mismatch_detected`, mirroring the `manifest_sync` non-destructive precedent.
- **Retention:** an hourly cron (`cleanup_runner`) hard-deletes rows whose `unlinked_at` is older than a 30-day retention window (`IDENTITY_UNLINK_RETENTION`), emitting `purged` events that preserve the identifying fields since the row itself is gone.
- **Six canon events** (`collaborator_external_identity.{linked,unlinked,drift_detected,unknown_external,purged,conflict_detected}`) are explicitly registered as infrastructure events, NOT added to `CanonLifecycleEventTypes` — they ride the same `event_log`/JSON-Schema/`EmitEvent` machinery but are categorized separately from core lifecycle events.
- **Rejected alternatives, explicitly:** adapters calling a Yggdrasil HTTP API directly (rejected — reverses the dependency direction, forces every adapter to ship an authenticated API client); a side-channel `identity.linked` AMQP event published by adapters (rejected — adds a new event type/listener for what's fundamentally adapter→core metadata, the envelope convention is simpler); hard-delete on offboard (rejected — loses audit trail, complicates re-onboard).

## Consequences

- Adapters opt in per-capability (`on_collaborator_created`/`scim_apply_user` write, `on_collaborator_offboarded` read, `on_webhook`, `list_identities`) — an adapter that implements none of these simply never gets external-identity context, which is backward compatible but means reactor behavior for offboarding is only as good as adapter opt-in coverage.
- The conflict-detection invariant (an active row can only ever map to one collaborator per instance) means any legitimate identity re-assignment (e.g. two employees swapping a shared service account) must go through an explicit unlink+relink, not an overwrite — a deliberate safety property, not an oversight.
- The webhook receiver becomes a new externally-reachable, HMAC-authenticated entry point per integration instance; a leaked webhook secret is a real attack surface, mitigated only by rotation via the instance's own credential store.
- Drift/unknown-external detection is passive (event-only); nothing auto-heals a drifted mapping — operators (or a future automation) must act on `drift_detected`/`unknown_external` events; a future ADR would be needed to change this policy.
- The 30-day soft-delete retention window before hard purge is a fixed platform default at this decision point — changing it means editing `cleanup_runner`'s threshold, not a per-instance config.
- yggdrasil-core code must never reference a provider name to implement this feature — verified post-implementation by grep; the only 9 hits found were the literal HMAC scheme discriminator string `github_hmac_sha256`, not coupled logic. This grep-based neutrality check is now a reusable verification pattern for future provider-touching features.
- Identity persistence failures are explicitly non-blocking to real lifecycle actions (onboard/offboard always "succeed" from core's perspective even if the identity write fails) — operators must watch metrics/events (`identity_link_dropped`, `identity_link_failed`) rather than relying on the primary action failing loudly.
- Every adapter that wants offboard correctness for non-email-keyed providers must adopt the envelope convention on write and the `_context.external_identity` read on subsequent reactor invocations — adapters that skip this silently keep the old, sometimes-wrong email-lookup behavior.
- Multi-repo blast radius: this decision requires coordinated adapter changes in `integration-slack`, `integration-google-workspace`, and `integration-github` to actually deliver value — the core table/API alone does nothing until adapters opt in.
