# G10 image-pair successor

The Source binds a qualified Core compiler R, OCI platform D, reviewed controller
inputs and the installed G9 predecessor. Activation requires a separately
qualified operational Source P, its actual successful CI attestation and a
byte-pinned operational package. Source bindings alone do not establish a
standing configuration, authorize a swap or prove production adoption.

The existing pair protocol from ADR-0100 is extended by one head, preserving the
complete image chain, all four historical authority axes and the installed G9
as the fifth. Seven helpers and 31 Owner methods are byte-identical to G9.
The original 41 protected references remain and the two actual G9 full120/own15
references must be independently supplied. The same per-boot consumed budget,
Cold/Hub lifetimes, runtime14, CPU limits and all-four network checks remain.

Runtime Source8/units2 and tools4 keep separate integrity rosters. The existing
six-command once-only swap protocol is retained. It makes no Core or provider
change. A separately reviewed `rollout/core_image_cas_once_g10.py` can later
perform one image-only Core PATCH after actual G10 qualification. Its only
maintenance mode is the exact failed child8b/f30 lineage adopting the original
settled destroy grant, with complete original rows and no unrelated busy work.
This mode confers no child-admission, Guest, nonce, lease, provider or retirement
authority. The previous G9 CAS and same-image replacement claims remain consumed.

The CAS consumes the unchanged e70 policy92 read-only SQL data as a hash-pinned
private input, preserving all eight terminal lanes, full history and strict M92
index checks. SQL statements retain 3s/500ms limits, 8s process custody and the
existing 120s CAS bound. Passing these predicates is not an admission mutex.
PATCH acknowledgement is not rollout, useful-work or business acceptance.

The existing CI job preserves all 180 prior IDs and adds the exact G10 roster.
Declared CI operands test Source behavior only; none represents an actual
standing config, signed release, cloud observation or Root approval. Local
functional execution is not part of this preparation.
